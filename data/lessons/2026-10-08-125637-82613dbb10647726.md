# Ruby’s Infinite Conveyor Belt—and the Power of Stopping

> **5 min · Ruby · Intermediate**

## The Hook

Imagine you run a small online bookshop. One morning, customers report that checkout occasionally fails. Your application has recorded its activity in a enormous log file: successful payments, page requests, background jobs, and the occasional ominous line beginning with `ERROR`.

You need the first three errors. Just three.

You write a tidy Ruby expression that reads the lines, keeps the errors, and takes three results. Yet the computer dutifully examines the entire file before handing them over. It behaves like a librarian who insists on collecting every detective novel in the building before lending you three.

The problem is hiding in a surprisingly ordinary word: **first**. Asking for a small result at the end of a calculation does not necessarily make the earlier work small.

Ruby has a way to change that arrangement. It can build a conveyor belt that moves only when someone at the far end requests another item.

## The Short Answer

Ruby’s **lazy enumerators** let you describe a sequence of transformations without immediately performing them. When you request results, Ruby processes values as needed, allowing a chain to stop once it has produced enough. This makes it possible to work with large files—and even endless sequences—without building every intermediate array. [Ruby’s lazy enumerator documentation](https://docs.ruby-lang.org/en/3.4/Enumerator/Lazy.html)

## How It Works

Start with two familiar tools. `select` keeps items that pass a test. `map` transforms items into new values. In their ordinary forms, with a block supplied, these methods return arrays: actual collections holding their results. [Ruby’s Enumerable documentation](https://docs.ruby-lang.org/en/3.4/Enumerable.html)

A **block** is a small piece of code handed to a method, usually inside braces or between `do` and `end`. In `{ |line| line.start_with?("ERROR") }`, `line` names the current item, and the expression checks its beginning.

Here is the bookshop investigation:

```ruby
# Assume shop.log contains:
# INFO started
# ERROR payment timeout
# INFO retrying
# ERROR inventory unavailable
# ERROR receipt failed
# ERROR another failure

errors = File.open("shop.log") do |file|
  file.each_line
      .lazy
      .select { |line| line.start_with?("ERROR") }
      .map { |line| line.chomp }
      .first(3)
end

p errors
# ["ERROR payment timeout",
#  "ERROR inventory unavailable",
#  "ERROR receipt failed"]
```

`each_line` provides an **enumerator** when called without a block: an object through which Ruby can visit the file’s lines. It supplies lines as iteration proceeds; it does not first return an array containing the whole file. `chomp` removes the ending line separator. [Ruby’s IO documentation](https://docs.ruby-lang.org/en/3.4/IO.html#method-i-each_line)

The important addition is `.lazy`. Now `select` and `map` describe stages of future work. `first(3)` requests three completed results and triggers the chain. [Ruby’s lazy enumerator documentation](https://docs.ruby-lang.org/en/3.4/Enumerator/Lazy.html)

Picture three workers beside the conveyor. One supplies lines, one checks for errors, and one removes trailing newlines. The customer requests three finished items. Rejected lines do not count toward that order.

For our sample file, the first line is rejected. The second becomes result one. The third is rejected. Lines four and five become results two and three. The sixth line never reaches the filtering block.

The investigation is finished before the conveyor reaches its end.

## The Fascinating Part

Remove `.lazy`, and ordinary `select` builds an array of **all** matching lines. Then `map` builds another array containing their transformed versions. Only afterward does `first(3)` choose three. The final request cannot undo work already completed. [Ruby’s Enumerable documentation](https://docs.ruby-lang.org/en/3.4/Enumerable.html)

This reveals a useful distinction: a sequence can be a collection of stored answers, or a description of how to obtain answers.

A restaurant menu does not contain dinner. It describes dinner you can order. Likewise, the lazy chain represents a process you can ask to produce values.

There is a tempting shortcut: take three lines before filtering. But that changes the question. “Find errors among the first three lines” differs from “find the first three errors.” In our sample, the shortcut finds only one. Moving a limit earlier can save work while quietly changing the answer.

Laziness preserves the intended order of filtering and transformation while allowing the consumer’s request to stop the process.

The file still matters. Three errors might occur near its beginning, or the third might be its final line. If fewer than three exist, this example reaches the end and returns those available. Laziness cannot know which unread lines contain errors; it avoids unnecessary processing after the request is satisfied.

Also, the demand for results belongs inside the `File.open` block. That block manages the file’s lifetime and closes it on exit. Returning an unfinished lazy chain and trying to consume it afterward would leave it depending on a closed file. Deferred work needs its resources to remain available. [Ruby’s IO documentation](https://docs.ruby-lang.org/en/3.4/IO.html#method-c-open)

## Think About This

Where in your own programs do you ask for a handful of answers only after making the computer prepare every possible answer?

## One More Thing

Ruby can describe an endless integer range with `(1..)`: start at one, with no final number. The range expresses a sequence rather than storing infinitely many integers. [Ruby’s Range documentation](https://docs.ruby-lang.org/en/3.4/Range.html#class-Range-label-Endless+Ranges)

```ruby
p (1..).lazy.map { |n| n * n }.first(5)
# [1, 4, 9, 16, 25]
```

This finishes because it asks for five squares. An attempt to collect the entire endless sequence would never finish normally. Ruby has not squeezed infinity into memory; it has given you a handle on a process whose next answer is always available. [Ruby’s lazy enumerator documentation](https://docs.ruby-lang.org/en/3.4/Enumerator/Lazy.html)

The conveyor belt can extend forever. Your order can still be five.
